Point items with negative values?

I only discovered this quirk by accident, as another result of 📝 my 2024 code cleanup. Back then, pbg's original formatting code for these point item popups contained one of the numerous code analysis warnings I chose to address rather than ignore:

e->point is unsigned, which surely means that you can never collect point items with negative values, right? Well, I was just testing a newly changed part of the architecture when this happened:

Surprise, the game does in fact not clamp point item values to 0! Looking at the collection value formula immediately tells us what happens there:

This works fine for regular gameplay where VIVIT's Y position is clamped to exactly 469. It also explains the 0 points you get for collecting point items while bottom-hugging with an empty Evade chain.

  1. Items only despawn after the collision check against VIVIT, giving them one additional frame below 487 pixels where VIVIT can collect them.
  2. Items accelerate at a rate of 3/64 or 0.046875 pixels per frame, up to a maximum speed of 6 pixels per second. Since VIVIT will collect any item whose center Y position is 23.984375 pixels higher than her own, this seems to result in (487 + 6 + 23.984375) = 516.984375 as the earliest Y position where a respawning VIVIT could collect items, reducing the window to just the 32 frames where VIVIT is between 516.5 and 470 pixels.
  3. But even with that limit in mind, stage scripts can (and do) spawn enemies far outside the bounds of the playfield, and shots and bombs can freely destroy them there.

Clearly though, we have to do something about this issue. But what, and how?

  1. First of all, the 5×7-pixel font used for these popups does not define a minus sign sprite. The original %d format specifier did add a minus sign into the string, but the popup renderer simply skipped over any non-numeric character. These negative point item values have always been part of the game, but the lack of a visible minus sign made their popups blend in with regular positive ones. If it weren't for code analysis convincing me to change %d to %u, we might have never spotted this entire issue.
  2. Secondly, the score displayed in the top-left corner of the playfield can only increase and never decrease. Negative score points therefore only really "exist" as part of the score delta, where they soak up points from other score sources until the delta gets positive again.

We could immediately reflect any negative deltas in the displayed total score:

However, that number isn't just some interim value, but represents the actual internal and official score that will be recorded in the High Score list, and consequently also in the future replay format. If there's any code path where the delta doesn't get fully added to the score before the game ends – such as 📝 at the end of TH04's Stage 6 and Extra  – we'd end up with a different score than the same gameplay would have gotten on pbg's original build.

Hence, we're left with fixing just the rendering bug of the missing minus signs, which is easily fixed by repurposing one of the various 5×1 pixel lines in #DCDCFE from the system sprite sheet.

So, let's split Shuusou Gyoku's game logic into a library! Step 1, obviously:

Defining the scope of "game logic"

On the one hand, the answer seems simple: The GameMove() function neatly lists all subsystems that are involved in a frame of gameplay. So let's take all of them, move them into a DLL, and then we're done, right? Well, there are several good reasons for not just taking this list of subsystems, and instead identifying and splitting off the actual minimum of gameplay-related code:

  • Performance. We'd ideally use this isolated game logic core for mass validation of every new release against every replay ever created. The few unneeded subsystems might only add a couple of milliseconds per replay, but that will quickly add up at this scale.

  • Thread safety, parallelism, and the associated refactoring effort. pbg stored most gameplay state in global variables, so we'd like to bundle all of it into a single C++ class that we can instantiate more than once. After all, 📝 process startup costs 30-40 ms on Windows, so it's much more preferable to multi-thread the replay validator instead. Minimizing the number of affected subsystems minimizes the amount of necessary refactoring work.

  • If we place all logic code in the new ssg/ directory and leave GIAN07/ with only the presentational aspects, anyone working with this codebase can immediately tell that modifying code in ssg/ runs the risk of forking gameplay and breaking existing replays. But the guidance and implicit documentation we gain from this physical separation can only be actually meaningful if we do make an effort to minimize the amount of code in ssg/ and maximize the amount of freely moddable code and data in GIAN07/.

  • While the game logic DLL will identify itself with the ReC98 release version number, I've also planned to hardcode a hash of all whitespace-stripped game logic source code. This hash will then be added to every replay as a second layer that can identify the game build a replay was recorded with. Hence, minimizing the amount of hashed code minimizes the chance for this identifying hash to change across versions or forks.

  • Right at the top of GameMove(), you can see a call to MWinMove(), which processes the game's dialog boxes. Due to my 📝 new lazily-updated immediate-mode approach to text rendering, each text box currently requires a dynamically allocated std::string to hold its exact contents. However, dialog also happens to be the only subsystem referenced in GameMove() that dynamically allocates during gameplay at all. If we can prove that this whole system doesn't affect game logic even with our planned support for showing dialog in the new replay format, we now have a good reason for keeping it in the frontend. And since we can prove it, this goes most of the way towards the pretty bonus goal of reducing C/C++ standard library bloat (and thus, OS API dependencies) in this future DLL.

  • And if we already don't want to include one subsystem, we might as well not include the correct number of subsystems.

Map tiles are probably the most notable case of decorative data that remains exclusive to the frontend. Since VIVIT never cares what she's flying over, the new logic layer not only doesn't have to process them and their scrolling, but doesn't even have to bother loading and decompressing any per-stage map data. All it needs are the ECL and SCL scripts from ENEMY.DAT.

Yup. Shuusou Gyoku uses a single RNG for everything from apparent gameplay aspects to decorative particles. The very first thing you learn about the kind of pseudo-random number generators that are used in replayable games is that they're stateful: Initializing them to a given seed will give you the same sequence of values, and every call to the rand() equivalent will move the internal state to the next number in the sequence. Therefore, every single subsystem that can possibly draw a number from the RNG's sequence must count as game logic by definition. If any of these subsystems are

  • processed in a different order (which would be a natural side effect of cleanly splitting game logic and apparent presentation), or
  • not processed at all (which would be the case for a CLI tool that runs just the game logic layer),

the resulting sequence of random numbers no longer aligns with the sequence that existing replays were recorded with, causing a more or less immediate desync.

On its own, this really doesn't look too bad or bloated. The 4 🚨-marked API calls aren't available on Windows 9x, but 📝 I already figured out how to deal with that last year. The bigger problem, however, is what this means for my plans of building a beautiful freestanding game logic library with low Win32 API dependencies. C runtime initialization is all-or-nothing, and if I throw it out, I can no longer even use sprintf() because those CRT locale pointers remain uninitialized.

  3. The non-standard %S and %C specifiers for formatting UTF-16 strings into char buffers

So, one feature where locale usage 📝 has, infamously, long been a notorious time bomb more than anything, one broken feature that only ever mattered for the very unsafe use case of non-hardcoded format strings (because MSVC's /execution-charset already checks the validity of hardcoded format strings at compile time), and a third feature that looks like mere non-portable syntactic sugar around a WideCharToMultiByte() call with that initial locale's codepage.

On the one hand, I wouldn't have expected such a crusty old API to correctly decode UTF-16 surrogate pairs and convert them into a valid sequence of UTF-8 bytes without falling into the CESU-8 trap. But was it really the best choice to make this conversion always fail with errno == EILSEQ on the first non-representable codepoint, instead of opting for any replacement character? And what's up with this codepage-dependent ASCII transliteration, where ä and ö get turned into a and o across the board, but Ÿ only gets turned into Y on CP1251 and is treated as invalid on CP932?

Latin-1, but without the Ÿ? Nope, this is something far worse:

Under the C locale, these format specifiers simply take the first 256 Unicode codepoints, truncate them to 8 bits, and fail on everything else, producing a byte string in an encoding that is neither valid ASCII nor valid UTF-8. The resulting bytes do happen to match the original string when interpreted as CP1252 in this case, but only because the last 75% of Unicode's Latin-1 Supplement block happen to match CP1252 and the first two characters fall into exactly that range. This is also why the Ÿ vanishes – as we've seen above, Ÿ is 0x9F in CP1252, but U+0178 in Unicode, so it fails the conversion. And if the UTF-16 string had contained any of the C1 control characters between U+0080 and U+009F inclusive, the resulting string wouldn't have been valid CP1252 either.

This ridiculous non-encoding is not just a recent fallback path, but traces way back to Microsoft C/C++ 7.0 from 1992, whose C runtime featured Microsoft's very first and preliminary implementation of the underlying wctomb() function. Back then, Microsoft hadn't yet implemented locales into the CRT either, so this protected cast from wchar_t to char was the only thing the function did.

  • ISO C specifies that wctomb() should use the current locale, but leaves the locale's encoding unspecified.
  • But as of 2016's XBD/TC2/D4/0029 amendment, POSIX now specifies that the default C locale shall encode exactly 256 characters in some kind of single-byte encoding.
  • This encoding is not specified beyond the stipulation that the ASCII character set must appear somewhere. Implementations are free to map ASCII to any arbitrary codepoints, and then choose whatever other 128 characters they like to support.
  • Obviously, it is completely absurd to amend a fixed 256-character encoding into a 2016 standard just because that's what the standard was always meant to say. But POSIX is always right. 🤓
  • And after all, this behavior is useful because it guarantees lossless round-trip conversions between narrow and wide representations as long as wide strings only use these specific 256 characters!!1! 🤓

Which leaves us with a state where both Microsoft and the POSIX police agree that this ancient code had better be kept around rather than removed. Backwards compatibility!

  • SDL offers a snprintf(), and we could abstract away the difference between it and the unsafe sprintf() used all over pbg's code. However, SDL only chooses its own no-nonsense implementation based on build-time availability of vsnprintf() – which is probably a given for most pre-compiled SDL packages on Linux and gets us right back to the system-specific behavior we were trying to avoid for a core piece of game logic. Not to mention that the logic DLL should explicitly not depend on SDL.
  • Type-safe, modern C++ alternatives like nanofmt are nice in theory, but highly disruptive in how they require a rewrite for every sprintf() call site. Also, code generation is highly disappointing, and we'd still need a solution for miniaudio's logger, which uses sprintf() as well.
  • Fortunately, there are plenty of minimal and no-nonsense sprintf() implementations out there that can work as drop-in replacements. eyalroz/printf ticks all the boxes, is actively maintained, and comes in at a very pretty 3.5 KiB of compiled code size in its most minimal configuration. Redirecting miniaudio to that implementation still requires silly header inclusion hacks though… Sigh, I want this library gone from this codebase so much.

C++ exception handling on MSVC

…and finally learn what all the related compiler warnings and flags actually mean. It starts with one thing:

warning C4530: C++ exception handler used, but unwind semantics are not enabled. Specify /EHsc

This warning originates from the few hilarious instances where pbg used exceptions for control flow. After rewriting them, we should be able to drop /EHsc again and be good…

OK, but the fact that some standard library functions might throw and catch exceptions should not have any impact on our code. So let's try a mixed approach: Compiling the standard library with /EHsc, but removing the flag for our own code. Well…

warning C5050: Possible incompatible environment while importing module 'std.compat': _CPPUNWIND is defined in module command line and not in current command line

Which we now get for every translation unit in the codebase. This warning is much worse than the other one: C4530 always points at a specific exception handler, but C5050 just points at the import and complains about a macro mismatch, breaking down the difference between activated and deactivated unwind semantics to a single preprocessor macro. Does this macro matter? How can we possibly say whether it does or doesn't?

So let's take a step back to C4530 and that initial module compilation. On the one hand, we'd fully expect to run into some restrictions if we wanted to code completely without bothering about C++ exceptions. But if we simply don't use any of these functions where MSVC emits C4530, we should be good, right? After all, C4530 defaults to just being a warning, not an error.

Well, not quite! As the diagnostic says, /EHsc is all about unwinding the stack in case of an exception – i.e., running the destructors of any local objects in scope while moving up the call stack to find a handler for that specific exception. And nothing else – you can still throw or catch exceptions just fine, but you just might leak memory or resources if you do.

That answers the question for our own code. But aren't we getting C4530 for standard library code that does catch an exception? Let's experiment with a feature where catching exceptions is crucial to its intended behavior, and where we can trigger it more easily than by occupying all memory:

And compile it with every permutation of /EHsc at std module level and source level, as well as with the final handler removed:

Amazing how C++ modules are still bleeding-edge enough to crash compilers, a full two C++ standard versions after they were introduced! Those weren't the only Internal Compiler Errors I've seen in this development cycle either, not by a long shot…

  • /EHsc and, by extension, C4530, don't seem to matter at all during module compilation. Any /EHsc setting on the module-importing source file seems to re-activate stack unwinding for any standard library code.

  • Why is that the case? Because neither std.ifc (the Built Module Interface file) nor std.obj (the compiled object file you're supposed to add to your link command line) actually contain any pre-compiled code. While it's clear that the IFC contains some sort of binary representation of the parsed and analyzed code, you might think that at least some pre-compiled code ends up in the .obj. But no, it only contains all static data referenced by the standard library. In fact, it can only ever contain data because all code in the std module comes from headers and therefore has to either be templated or declared as inline to maintain the One Definition Rule. Thus, the binary representations from the IFC file only get instantiated and specialized in each translation unit they're imported into, under that unit's exception handling rules. MSVC's frontend probably emits C4530 in a much too early analysis stage, way before the absence of /EHsc would actually matter.

  • The only critical case is the very first one, where we do catch without /EHsc, and therefore skip running destructors you would expect to be running. In this case, however, MSVC emits C4530 precisely to protect us from this exact issue. This specificity shoots C4530 right up there towards GCC's 📝 -Wformat-overflow as one of the best diagnostics ever emitted by a C++ compiler.

  • Because we can now derive a rock-solid strategy: Disable C4530 during module compilation, but treat it as an error on all other build command lines. This allows us to safely compile everything without /EHsc, because we'd now get a compile error as soon as we write code where the absence of /EHsc would matter.

  • And as a nice bonus, MSVC can now properly optimize DLL-exported class constructors as it no longer has to accommodate exceptions flying across DLL boundaries.

So, we got pretty far, but in the end, did all this bloat reduction really matter? Absolutely, if you ask me:

We've learned something about two unfortunate aspects of the C and C++ standard libraries, got rewarded with a beautiful, small, and freestanding binary that natively runs on every Windows version since 95, and we didn't even have to screw around that much to make it happen, despite still compiling with current Visual Studio. When I went into this, I assumed that we'd have to use /NODEFAULTLIB and link to at least SDL's C runtime polyfills, but we didn't even have to do that. Instead, the DLL still gets to use security cookies, MSVC's built-in functions for 64-bit math on 32-bit x86, and a wide range of modern C++ standard library features, including std::unique_ptr with adopted raw pointers and custom deleters, ranges and views, spans, and std::invoke.

Alright, I'm happy with the build quality, so on we go to Step 2 of the actual mission:

Completing the separation of game logic

Which certainly was the most grueling part of this development cycle. Even round initialization required a good part of a full push just to clean up the code and end up with a consistent API that works for regular 6-stage rounds, Extra Stage rounds, replays, and the pre-recorded demos. This codebase is truly cursed: You take a look at a new piece of code, notice that it's a mess of procedural state mutations, and just have to streamline it before you even want to touch anything. 😩

So, how do we get to our single C_SSG class that bundles all game state and offers a central method to run a frame of gameplay based on player input? If we want to keep code changes to a minimum and not basically rearchitect the entire game from scratch, there are two realistic paths from the code's original bunch of globals and functions:

  1. Throw all gameplay state and functions into a single class. This would remove quite a few header files, but the .CPP files would stay largely identical, mostly only requiring changes to the function definition headers from free-function to class method syntax: On the other hand, we'd then have a god object, and every change to its class declaration would trigger a recompilation of every .CPP file in the logic DLL.
  2. Retain the code's original subsystem separation, turn each subsystem into its own class, and restrict the possibilities for rampant state mutation by only giving each subsystem the references to the other subsystems it actually needs. A few of these references can then even be const, providing additional safety and documentation of intent. C_SSG then bundles all of these smaller classes and acts as a giant switchboard connecting all the subclasses to each other. This maintains the game's existing code structure at the cost of hundreds of lines of reference management boilerplate. We do get to make good use of forward declarations to keep header dependencies to a minimum, though.

Initially, I gravitated towards option 1), but immediately disliked it mere minutes after I started typing. So, one class per subsystem it is. This is slightly more disruptive to the .CPP files in how we get an extra change to each function call between subsystems, but those are trivial to review. In most cases, it's just an additional dot accessor between two camel-cased words.

And just in case you're wondering how large C_SSG ended up being in the end: 403,616 bytes on 32-bit systems, and 405,984 bytes on 64-bit systems.

I did have to make a few more interesting implementation decisions as part of this whole logic/presentation split and the resulting API:

  • You might have already noticed it from the KERNEL32.DLL import list above, but yes, I decided to not add any file I/O to the game logic DLL. It made much more sense to leave that to whatever language the DLL is used from: The high-level file I/O functions of such languages are typically more convenient to use, and often provide far superior error handling than whatever I could cobble together across a FFI boundary.

  • Speaking of FFI usage, this was another key design goal of this library. After all, we'd ultimately like this code to perform replay validation on Silent Selene's server, which is written in Python. It also stores replays in a PostgreSQL database, so it will certainly appreciate not having to write out replays to the file system before being able to pass them to game logic code.

  • For the most part, the separation of logic and presentation continues to work as it did with the original code's split between GameMove() and GameDraw(): The logic layer runs one frame of gameplay, and the frontend's renderer can then take the resulting state and draw it. However, there are still several events that can happen in the middle of a frame, triggered by conditions and with parameters you couldn't pull from game state at the end of the frame. Sound effects are the most obvious example, but these kinds of events would also need to occur for the majority of SCL instructions, including all kinds of background effects and the entirety of the in-game dialog system. I could have put all of these events into some kind of queue to be processed at the end of a frame, but that would have required allocations and introduced a whole new problem of needing to snapshot a whole lot of data at the time of the event, just to ensure that we fully match the original game's behavior. So, classic hooks via C function pointers it is.

  • And since it doesn't really fit anywhere else: Obviously, the Linux version also gets a libssg.so.1.v1.005, together with the version-less linker-name and versioned SONAME variants as per the usual shared library conventions. Usually, the latter two would form a symlink chain that ultimately points to the real shared object containing the actual code. Unfortunately though, this naive approach would really degrade build performance under Tup in particular. Despite Tup's Unix-centric origin, Tupfiles really prefer the Windows approach of a separate import .lib file that defines the API surface of a DLL. If we then use the ^o^ flag in the DLL's link rule and build a new version of that DLL, Tup can then skip needlessly re-linking any dependent binaries if the newly created import .lib is exactly identical to the old one. On Linux, though, the final target behind libssg.so (which is what linkers read when you specify -lssg) is essentially different on every code change, triggering a rebuild of every dependent binary and thus kind of defeating a big point of shared libraries.

One hidden change concerns the game's debug mode. pbg's original code had a debug option to turn off collision detection, which he implemented by conditionally returning from the "VIVIT got hit" function based on a debug-exclusive flag. Unfortunately, this kind of debug feature creates massive conceptual problems for what we're trying to do here:

  • Since our library should be able to process multiple game states in parallel, this should no longer be a global flag. CLI and logic API users should not have to split replays into two batches based on whether the flag was set or not. Thus, this must be another round parameter.
  • However, the fact that this wasn't a proper round parameter also means that the flag wasn't propagated into pbg's old replay format at all. Hence, it's already impossible to identify existing replays recorded with the Hit option turned [O F F] from their header data alone. The CLI will help identify such replays (since running them with collision detection enabled is likely to cause a desync at some point), but it can't definitively tell either.
  • But if the replays don't contain this flag, who sets it? Well, it would continue to be passed from the frontend – i.e., the game and the replay CLI, introducing one more command-line option to the latter. And then we're right back to where we started, forcing users to manually track a replay-specific property as part of the simulation environment.
  • We could start tracking that flag from now on, repurposing one of the various unused bits in pbg's replay header. But should we really open a door for cheaters by having such a round parameter in the first place?
  • We could continue limiting this feature to debug builds. But do we really want to continue having separate behavior between Debug and Release builds, and add separate API contracts on top? 😵

That's way too many questions without easy answers for a minor debug feature that non-developers won't ever even encounter. Just removing it seems to be the easiest way forward, but on the other hand, this kind of feature is vital for debugging.

Maybe, we can even restore the original feature once we have that new extensible replay format and have implemented all the required bureaucracy for the highly requested quirk toggle. That would already create at least one replay-incompatible gameplay fork, after all. But for now, this is what we're going with.

Now that the codebase has to produce two more binaries than it did before, I also had to reconsider the physical layout of the repo, and how to best share any code that needs to be shared between any of these binaries.

And so, the completed feature ended up calling for the game-independent code to be modularized along a total of four different axes:

  • A logic layer that provides a few small bits of code on top of the C++ standard library module, provides eyalroz's printf library, and adds no further dependencies. Since it mostly defines types, classes, and templates, and comprises very few translation units on its own, it's small enough to get statically linked into all three binaries.
  • An app layer that contains all the helpers on top of SDL that we want to use in both the game and the replay CLI, as well as the SDL dependency itself.
  • An API layer. This one currently only contains functions to retrieve game logic and ReC98 build version strings. Only exists because I needed an additional game-independent layer that gets linked into the game logic DLL but not into the CLI or game binary, since they should always pull these versions from the DLL.
  • And finally, an engine layer that gets all the remaining code required for the main audio-visual gaming experience. This layer also bundles all remaining third-party dependencies such as libogg/libvorbis, dr_flac, libwebp, and miniaudio.

A replay validation CLI

Correctly initializing replays in such a CLI posed a final slight challenge. Since pbg's single-stage replay format doesn't actually store the stage in its header, we can only possibly derive a replay's stage from its filename. We could just enforce the same 秋霜りぷ*.DAT filename scheme that the original game's replay menu expects, but that idea quickly fell apart in the face of even my current existing Shuusou Gyoku replay collection, which features multiple descriptively named replays for every stage. I'd obviously prefer to analyze the whole set with a single * glob.

This need to handle Unicode filenames also brings us to what might seem like one of those typical strange ReC98 engineering decisions. The app/ layer's dependency on SDL might have already given away that I chose to write this CLI entirely on top of SDL's standard library and logging functions. Typically, you wouldn't consider using a low-level game library for a CLI tool, but there are several good reasons for SDL in particular:

  1. Unicode command-line arguments just work without me having to write a single line of platform-specific code. That feature is obviously crucial given the filenames this tool usually needs to process. It sure is nice that I don't have to solve the same problems all over again.

  2. Same for Unicode console output on Windows. The only platform-specific code we actually need stems from SDL's unfortunate choice of outputting to stderr rather than stdout, requiring a few slightly ugly lines of code.

  3. Thanks to SDL_GlobDirectory(), cross-platform globbing support for systems without powerful shells was a quick and cheap addition. We might even get recursive globbing via ** as soon as someone sends a PR. The enforced separation of path and filename parameters slightly complicates the usage of this function, but it's actually not too bad. Certainly much simpler than sticking to the C++ standard library, which would require approximating globs by converting them to regexes and matching all files by hand.

  4. SDL is part of all Windows and Linux packages anyway.

  5. Ultimately, this CLI is meant to serve two goals: A general demonstration of the fact that Shuusou Gyoku's game logic now has a headless API, and a tool that will ultimately facilitate mass validation of every replay ever recorded, as part of my release pipeline. Depending on how I'm going to approach validation, I may or may not add support for a more machine-readable output format. Regardless, the CLI is meant to demonstrate the API, not the other way round.

  6. If you remove all the argument parsing and globbing code, you're left with roughly 60 lines of C++ code that use the DLL's API for loading ENEMY.DAT and the replay, and looping over every frame. And that's with error handling at every step of the way. Shelling out to the CLI and parsing its output probably takes more code than just calling the same C API of the game logic DLL from your programming language of choice. And given the months of work that went into boiling down this API into only its most elementary steps, it's likely to remain stable for quite a while.

  7. Since almost everything in the CLI is a call to either an SDL or logic DLL function, I can remove the C++ runtime initialization on Windows at, once again, little additional cost, and end up with a 9 KiB binary! I might assign way too much importance to these optics, but I love how this clearly communicates that the CLI contains no additional magic whatsoever, even if you don't read its source code.

Alright, we've kept everything nice and minimal, but how fast can we actually simulate gameplay if we don't have to render anything?

Yup. That's 7 minutes of Extra Stage gameplay simulated in less than 200 ms on an 8-year-old midrange CPU. Running single-threaded 32-bit code that suffers from MSVC's horrid codegen and still has several untapped optimization opportunities. I would have been happy if game logic ran 20% as fast as this. But with those numbers, I can confidently cut multithreading from these 6 very packed pushes and delay it until we actually have masses of recorded replays to validate.

But it gets even better. The ssg.v1.005.dll I've been talking about is not only used by the regular modern build, but also by the Windows 98 one. Hence, we've even achieved this level of performance by sticking exclusively to i586-era x86 instructions. You might object to the mere idea of giving up performance in exchange for a cleaner game directory, but:

Why complicate the build and add another file for a ~5% speed improvement when a regular 64-bit Linux build, targeting the baseline x86-64 ISA from 2003, will already run somewhere between ~7% and ~13% faster? And if this ever turns out to be too slow after all, I'd rather explore algorithmic optimizations instead of staring at individual instructions.

Future work

Even with the Hatoyama split, I had to cut a few minor corners to get this feature out the door at all within the funding it received:

  • Packfile compression (which includes the 秋霜りぷ*.DAT replay format) could be part of the logic DLL. This currently prevents procedural replay generation without third-party repacking tools.

  • Swappable game logic layers. Ideally, modders should be able to ship gameplay mods by just sharing logic DLLs with unique names that players should then be able to select in a menu or by specifying a CLI parameter. You shouldn't have to re-link either the game or the CLI just to use a different logic DLL.

  • The generated code of the logic DLL is so embarrassingly bad in parts that I'm seriously considering switching the Windows build to MinGW – especially now that there is a really good fork that focuses on targeting old Windows versions with recent versions of GCC. It also happens to be maintained by responsible developers who agreed to avoid a classic MinGW packaging trap. If we decide to abandon 📝 the current strategy of trying to chase Windows 98 support with current Visual Studio, we could probably reduce costs for the Windows 98 build by a fair amount. (And finally uninstall that piece of bloat!)

  • If you just want to do me a favor: It really is time we got away from miniaudio. 😩 SDL 3's audio API would remove bloat and compilation pain for the modern build, and moving the Windows 98 build back to raw DirectSound with backported support for waveform BGM would significantly reduce that build's audio latency, especially on VMs.

After all the cross-platform engine work I did for Shuusou Gyoku over the past years and all the code splitting I did for this release, applying it all to a second game could be done pretty quickly. Of course it will have a few challenges of its own, but its codebase looks much cleaner at first glance, and doesn't suffer from the awful 8-bit rendering and replay preservation constraints that Shuusou Gyoku suffers from. I'm confident that I can now port this game in a fraction of the time it took me to port Shuusou Gyoku.
