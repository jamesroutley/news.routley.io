Programming at Light Speed: Building the Gravity Query Engine

With the release of pgrust v0.4-beta, our new query engine, Gravity, is now as much as 3x faster than ClickHouse on ClickBench, the benchmark that ClickHouse themselves designed to show off how fast ClickHouse is. Even better, Gravity achieves that speed while supporting the full Postgres SQL dialect and type system.

In a couple of previous posts, I wrote about how we used batching, operator fusion, and SIMD to make pgrust hundreds of times faster than Postgres for analytical queries, and how we built a copy-and-patch JIT compiler that compiles stencils in 5 microseconds. All of that work, built up over several releases, is what became Gravity.

Copy-and-patch was a great starting point, but gluing pre-compiled templates together only gets us so far. Because we did not have a real intermediate representation or register allocation across the whole loop, we ended up leaving a lot of performance on the table compared to an optimizing compiler like rustc or Clang. For pgrust v0.4, we wanted to go all the way and build a query compiler that generates optimal machine code for any SQL query. That is why we built Gravity.

Normally, when engineers try to make software faster, they work from the bottom up. They run a benchmark, look at a flamegraph, find a hotspot, and figure out how to speed up their code by 15% or 20%. The problem with working from the bottom up is that you don’t know what the ceiling is. You might be 20% away from the fastest possible code the hardware can run, or you might be 100x away.

When we started building Gravity, we flipped this question around. We asked ourselves: how fast can a database actually be? Instead of incrementally speeding up our existing query engine, we wanted to start from the physical speed limit of our hardware and file format and work backward. I like to call this “programming at light speed”.

To find out what “light speed” looked like, we had Claude write standalone, heavily optimized Rust programs directly against our columnar storage crates for a corpus of analytical queries. These programs bypassed the entire SQL executor and just ran hand-tuned, multithreaded Rust loops with SIMD directly over our on-disk format. When we ran those handwritten Rust programs, they executed queries roughly 4x faster than existing analytical databases like ClickHouse across the board. We then mined those hand-tuned Rust loops for optimizations we could incorporate into Gravity.

Our goal for Gravity became simple: for any SQL query, JIT compile machine code at runtime that gets within 20% of the handwritten Rust code Claude wrote directly against our file format.

The General Architecture of Gravity

Our main goal when designing Gravity’s architecture was to give ourselves a ton of flexibility in the generated output. We knew that if we made it easy to change Gravity to emit whatever low-level optimizations a query needed, it would become much easier for us to close the gap and approach light speed.

Instead of hardcoding execution patterns or stitching fixed stencils together, we structured Gravity as a multi-stage compiler pipeline that progressively lowers a high-level Postgres plan down to raw assembly:

SQL Query
  -> Postgres Plan
  -> Pipeline Graph
  -> Lisp IR
  -> Assembly

To see what a query looks like at each stage of the compilation process, let’s take the following query:

SELECT UserID, extract(minute FROM EventTime) AS m, MIN(URL), COUNT(*)
FROM hits
WHERE URL LIKE '%google%'
GROUP BY UserID, m
ORDER BY COUNT(*) DESC
LIMIT 10;

Stage 1: The Postgres Plan

Gravity does not replace Postgres’ parser or query planner. When the query arrives, the pgrust planner analyzes the table statistics and produces a standard query plan.

Limit (cost=... rows=10)
  -> Sort (Sort Key: count(*) DESC)
       -> HashAggregate (Group Key: userid, extract(minute FROM eventtime))
            -> Seq Scan on hits (Filter: (url ~~ '%google%'))

Stage 2: The Pipeline Graph

Next, Gravity takes the query plan and converts it into a “pipeline graph”. This is an intermediate representation that expresses how data will flow throughout the query execution. Each pipeline represents how a row is transformed and operated on throughout the query.

Here is a sketch of what the Pipeline graph looks like for our query:

graph pipelines=3 breakers=2 root=p2

p0 eligible end=breaker(slot=0 HashAgg)
  source range rel=hits am=pgrc
    lanes Attr(UserID):byval8 Attr(EventTime):byval8 Attr(URL):dict4
  filter like(URL, param0)
  project (key0=UserID, key1=extract_minute(EventTime), agg0=min(URL), agg1=count_star())

p1 serial end=breaker(slot=1 TopK)
  source breaker slot=0
  topk k=10 order=agg1:DESC

p2 serial end=sink
  source breaker slot=1
  project (UserID, m, min_url, count) -> wire

In this case, the query is split into three pipelines:

  • p0 takes the rows out of the hits table, filters for rows where the url contains “google”, and then inserts the rows into a hash table to calculate COUNT(*) and MIN(url) grouped by the user_id and minute of the event time
  • p1 takes the resulting hash table and puts them into a heap of size 10 to calculate the 10 groups with the highest COUNT(*)
  • p2 takes the resulting heap and pulls out the rows and sends them over the wire

Stage 3: The Lisp IR

Next, Gravity compiles each pipeline into a single function in our Lisp-based, assembly-like intermediate representation. Because the IR is general, we can fuse the scan, filter, projection, and aggregation inside p0 into whatever loop structure we want. Here’s a sample of the code for p0:

;; ── loop head: one trip per row ─────────────────────────────── (Seq Scan)
(block b210 ((v2574 i64) ...)                   ; v2574 = row index; loop state rides along as block params
  (v2585 (icmp slt v2574 v103))                 ; more rows in this batch?
  (condbr v2585 (b211) (b35 ...)))              ;   no -> fetch the next batch

(block b213 ((v2587 i64))                       ; ── read the row's columns ── (Seq Scan)
  (v2591 (ptr_add v105 v2587 8 0))              ; &EventTime[row]
  (v2592 (ptr_add v109 v2587 8 0))              ; &UserID[row]
  (v2593 (ptr_add v113 v2587 4 0))              ; &URL[row]   (dictionary code)
  (v2612 (loadz i32 v2593 0))                   ; ── WHERE URL LIKE '%google%' ── (Filter)
  (v2616 (load i64 (ptr_add v2605 (ushr v2612 6) 8 0)))
  (v2621 (iand (ushr v2616 (iand v2612 63)) 1)) ;   one bit per distinct URL
  ;; …                                          ;   row fails -> straight to the next row
  )

(block b227 ()                                  ; ── extract(minute FROM EventTime) ── (Projection)
  (v2695 (load i64 v2591 0))
  (v2711 (iadd v2695 211813660800000000))
  (v2715 (umulh (ushr v2711 10) 10746007285463371))
  (v2720 (isub v2711 (imul (ushr v2715 11) 3600000000)))
  (v2726 (ushr (imul (ushr v2720 8) 18764999) 42)) ; minute
  (v2732 (load i64 v2592 0))                    ; UserID
  ;; …
  )

(block b229 ()                                  ; ── GROUP BY UserID, m ── (HashAggregate)
  (v2897 (icmp eq v2576 v2732))                 ;   same UserID as the group in registers?
  (v2898 (icmp eq v2577 v2739))                 ;   same minute?
  (v2899 (iand v2897 v2898))
  (condbr v2901 (b249) (b250)))                 ;   no -> write it to the hash table (b250), start a new group

(block b249 ()                                  ; ── MIN(URL), COUNT(*) ── (HashAggregate)
  (v2903 (loadz i32 v2593 0))                   ;   this row's URL code
  (v2911 (icmp ule v2903 (iand v2581 4294967295)))
  (v2912 (select v2911 v2908 v2581))            ;   MIN: keep the smaller code
  (v2921 (iadd v2584 1))                        ;   COUNT(*) += 1
  (br b228 v2576 v2577 v2578 v2579 v12 v2912 v2913 v2915 v2921))

(block b228 (...)                               ; ── next row ──
  (br b214 ...))                                ; -> b214: row index + 1 -> back to b210

Finally, we have backends for each target that compile the IR into assembly:

Starting from the Bottom: Designing and Benchmarking the Lisp IR First

The first part of Gravity we built was the backends. We wanted to prove that our IR and code generator were actually capable of matching rustc -O3 before we built a SQL compiler on top of them. Once we had the Lisp IR and the backends working, we tested them by having Claude write optimized IR programs that mirrored the previous handwritten Rust code.

Benchmarking those hand-written IR programs gave us a huge piece of news: our Lisp IR compiled in under a millisecond and ran within 10% to 20% of the handwritten Rust code compiled by rustc. Even more importantly, across almost every query we tested, we didn't need to invent any fancy new IR instructions. The IR was expressive enough that the entire gap between our naive SQL engine and "light speed" came down to compiling SQL queries to the IR.

Teaching the Planner New Algorithms

When we compared Gravity against Claude's handwritten Rust across our query corpus, we found queries where the handwritten code was still orders of magnitude faster, not because of how it compiled the loop, but because it was running a fundamentally different algorithm. Even though we kept Postgres’ planner, standard Postgres plan nodes could not express the light-speed algorithms. We had to make sure our plans could encode them.

Across the queries we optimized, we found three algorithms we needed to add to the planner. All three algorithms are specific to a columnar format, so it makes sense that the Postgres planner can't support them. Keep in mind that for a columnar table, you usually specify a sort key, so the data is usually in an order that places similar values close to each other. The three algorithms:

  • ZoneWalk - For a query like ORDER BY … LIMIT n, Postgres would execute this either by using an index or by scanning the whole table. pgrcolumnar enables an additional way of executing the query. pgrcolumnar breaks the table into batches of 8192 rows called granules. Each granule has metadata that tracks the min and max values for that batch. Instead of scanning the whole table and sorting to find the top n rows, we use the min/max bounds to read the granules in order and stop as soon as n rows are resolved.
  • ZoneTopK - For a query with the shape GROUP BY ... LIMIT n, we can use an algorithm very similar to the ZoneWalk. Instead of scanning the entire table and hashing every row just to return n groups, we can use the metadata to walk the granules in order by the GROUP BY key. Once we have seen n complete groups whose maximum possible keys are below the minimum key of every remaining batch, we can stop scanning immediately. ClickHouse 26.10 has a similar optimization, enable_group_by_top_k_dynamic_filtering, which also requires complete groups.
  • TwoPass - For a query of the shape GROUP BY ... ORDER BY count(*) DESC LIMIT 10, if one of the columns in the group by has high cardinality, it can be faster to execute the query in two passes:
    1. Compute an upper bound on the size of each group by counting rows per key: SELECT unique_key, COUNT(*) ... GROUP BY unique_key
    2. Then go back and fetch only the groups whose upper bound is big enough that they could make the top 10

This works because the most expensive part of the query is the first pass. You’re able to save a lot of memory bandwidth by fetching only one column on the first pass and then fetching the rest on a second pass

All three of these plans were added as costed plans to the pgrust planner. At plan time, the planner estimates how many granules a walk will actually have to read before stopping, and only picks the rewrite if it is cheaper than the standard scan.

Now that our queries used the same algorithms as the light speed implementations and we knew our IR was fast enough to compile our query plans, the last step was compiling SQL to our IR.

Optimizing SQL→IR Compilation

For the SQL→IR compilation, all that mattered was how optimized we could make the IR. Because we used the same algorithms as the light-speed Rust programs, we could diff our code against the Rust code and see where the differences came from. This led to over 100 optimizations. Here’s three of them to give you a sense of what makes Gravity so fast.

1. Inlining Function Calls and Aggregates

In standard Postgres, evaluating a SQL function like extract(minute FROM EventTime) or updating an aggregate like AVG or MIN makes a function call through Postgres's function manager (fmgr) on every row. Making a function call once per row (or even once per small batch) completely destroys performance.

To fix this, we categorized all of Postgres's built-in functions into tiers and, for 238 core functions and aggregates, we directly inline them into our Lisp IR. A query with a COUNT(*) and SUM will instead look something like this:

(block b32 ()
  (v313 (load i64 v307 24))         ; load count from aggregate state
  (v314 (iadd v313 v194))           ; count + 1
  ((store v307 24 v314))
  (v315 (load i64 v307 32))         ; load sum from aggregate state
  (v316 (iadd v315 v309))           ; sum + val
  ((store v307 32 v316))
  (br b22 v197))

Benchmarking the performance of AVG, inlining dropped the loop from 392 instructions per row down to 120 instructions per row and made the query 2.56x faster.

2. Late Materialization

In our columnar format, text columns like URL are dictionary-encoded: each part of the table stores a dictionary of unique strings, and the rows themselves store integer codes into the dictionary.

Our early versions of Gravity decided how to emit IR for an expression based only on its SQL type (TEXT, INT4, NUMERIC). Because url has the SQL type TEXT, Gravity decoded the dictionary code into a string and copied it into every row. When we looked at Claude's handwritten Rust for these queries, it never touched strings inside the row loop. It used late materialization. It operated on the dictionary code for as long as possible and only materialized the actual string at the very end.

We redesigned Gravity so that every value is materialized as late as possible. When computing a filter such as url LIKE '%google%' on every row, the compiler emits a step that runs our heavily optimized substring matcher once per unique entry in the dictionary and creates a bitmap of which dictionary codes match the filter. By default, v0.4-beta keeps that bitmap in server memory, keyed by the filter with its constants and by the table part, so a later query with the same LIKE on unchanged data reuses it instead of running the matcher again. Setting pgrust.dict_filter_cache = off, or pgrust.condition_cache to granule or off, makes every query build its own.

To compute an aggregate like MIN(URL), Gravity doesn't compare strings per row. The compression dictionaries are sorted, so for two strings encoded from the same dictionary, the string with a smaller code is the smaller string. Because of this, when computing the minimum string within a range of rows compressed with the same dictionary, it becomes mostly integer comparison rather than string comparison.

3. Run Collapse in Registers

Even when our filter and expressions are inlined, probing a multi-key hash table on millions of rows is expensive.

When we compared Gravity’s output against Claude's handwritten Rust on GROUP BY ... queries, we noticed something interesting. In real-world tables, values for a column like UserID or event timestamps are often partially clustered on disk, meaning we frequently see runs of consecutive rows that belong to the exact same group. Claude's Rust code exploited this by keeping the current group's keys and running count in local variables (which rustc kept in CPU registers). As long as the next row had the same key as the previous row, it just incremented the counter in a register and only probed the hash table when the run ended. On a 100-million-row table, that collapsed 100 million hash table probes down to 22 million.

We modified Gravity to track the previous group key and probe the hash table only when a new group key is seen.

Making Sure It Generalizes

One challenge we had when building Gravity was there was a tendency for Claude to overfit the optimizations to our corpus queries. Often Claude would write the optimizations only for exactly the query we were benchmarking. If a user writes strpos(URL, 'google') > 0 instead of URL LIKE '%google%', or groups by a column wrapped in a Postgres DOMAIN type, a brittle pattern matcher will miss the fast path and silently fall back to slow code.

To counteract that, we made a catalog of every optimization. We then wrote a fuzzer that took a single optimization and tested it across many different query shapes. It would try a variety of types (int2, int4, int8, numeric, text, domain) group bys, and much more to confirm the optimization kicked in across many queries and not just one. Dan Luu wrote about how much testing goes into pgrust, which has also turned up real bugs in Postgres itself.

Where Gravity Stands Today

Designing our Lisp IR against handwritten Rust first, and then teaching Gravity to emit inlined, late-materialized, register-optimized IR, got us remarkably close to our "speed of light" target. Across a wide range of analytical queries, Gravity's runtime JIT compiles queries in under a millisecond and executes within 10% to 20% of the handwritten Rust code Claude wrote directly against our file format.

When we isolate the query engine by running the exact same pgrust binary over the exact same columnar table with Gravity turned on versus our Volcano row executor, Gravity is 102x faster cold and 499x faster hot, and runs as much as 3x faster than ClickHouse while supporting Postgres's full SQL dialect and type system. For anyone coming from Postgres: on ClickBench's c6a.4xlarge machine, pgrust v0.4-beta's combined score is more than 1,000x better than PostgreSQL 17's, and 1,365x better on cold runs.
