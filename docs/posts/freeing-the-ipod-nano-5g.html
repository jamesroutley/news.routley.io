Freeing the iPod Nano 5G

A few years ago, CUB3D demonstrated unsigned code execution on the iPod nano 6G and 7G through ipod_sun, a font-based exploit. Whether the same approach would work on the 5G was still an open question.

I wanted to get Rockbox running on the nano 5G, so I set out to adapt the exploit. My motivation was simple: an up-to-date music player without an internet connection. I built a fully untethered boot chain that loads Rockbox from the nano 5G’s NAND, with no computer or button sequence needed after installation. I also found a way to make the existing exploit fully untethered on the nano 7G, and likely the 6G too.

Existing DFU exploits, including q3k’s wInd3x, provide code execution on the nano 5G, but booting custom code this way requires a computer each time. I used wInd3x to explore the device and develop a convenient, fully untethered exploit. The firmware details below refer to the latest nano 5G firmware, 1.0.2 (34A20020).

The catch with ipod_sun

The nano 5G’s NAND flash appears through a flash translation layer (FTL) as a logical disk with 4 KiB sectors. Its partition table separates a small private area for persistent device state, a firmware partition containing boot programs and resources, and a data volume for user files. The firmware partition has a directory of named images; the fonts live inside rsrc, a resource volume formatted as FAT16.

The original ipod_sun chain combines a resource-validation bypass with a font-parser vulnerability. Apple’s firmware directory identifies the normal operating system as osos, the disk-mode program as disk, and the resource image containing fonts as rsrc. The disk-mode boot path does not request the resource signature check used by normal OS boot.

Swapping the disk and osos directory entries exploits that difference: selecting disk mode now launches Apple’s regular OS under the disk-mode policy. The OS still reads its fonts, but the bootloader has not required a valid signature for the modified resource image.

The font then triggers CVE-2010-1797, the FreeType CFF stack-overflow vulnerability also known through the star exploit. A malformed font program corrupts the parser’s stack and redirects execution. My 5G port adapts that technique to the device’s font and execution context.

The swapped images remain on disk, but each restart still requires choosing disk mode with the device’s buttons. A normal boot selects the other entry. I wanted a better experience, with the modified font loading through the normal OS path.

Finding a bypass in the normal boot path

The bootloader is organized into EFI-style modules stored as Portable Executable (PE) images. The module that passes execution to the next boot stage decides whether to validate rsrc. It first asks the PrivateData module for FirmwareStatus, which comes from an authenticated record in the private NAND partition.

A value of 2 returns success before the resource-validation query. Bit 0 must remain clear: it is checked first, so 3 would reject the boot attempt. Tracing the restore OS shows that it sets the status to 1 during firmware transfer and clears it to 0 at the end. This suggests an update-in-progress guard that prevents booting an incomplete installation.

Apple’s resource-mount path writes status 2 only on the first successful boot, after rsrc has passed signature verification. My hypothesis is that this avoids repeating signature verification to shorten boot time or reduce energy use.

This is the second bypass. Instead of disguising the normal OS as disk mode, I can leave the firmware directory alone and supply a valid private record with bit 1 set. The normal boot path then accepts the modified resource image, and its font delivers code execution automatically.

The record lives in the private partition, identified by MBR type 0x3e. On the 5G layout I examined, the partition begins at logical block 1, with 4 KiB blocks. The bootloader reads a 512-byte header from its start. The status-bearing format begins with the little-endian magic PRVD and has this layout:

The integrity tag is device-specific, so creating and saving a valid PRVD record requires code execution on that iPod.

The tag is the first 16 bytes of the SHA-1 digest, encrypted with the device’s hardware AES UID key, selected through key slot 2. It authenticates the private header, but as the authentication is constructed on device we can falsify it if we have code execution.

Using emCORE to make it persistent

To inspect and update the private partition, I adapted emCORE, an older framework from freemyipod’s earlier iPod exploitation and boot work. It provided an existing USB-controlled environment to extend for the 5G.

I wrote the nano 5G NAND driver and integrated it into emCORE alongside the flash translation layer (FTL) and hardware AES access. I’ll cover the flash memory sequencer subsystem (FMSS), which enables NAND writes, in a future post. The FTL presents logical sectors over physical flash; it is the layer through which I read and write the private record and install the modified font.

The private-status tool verifies the existing header and tag, constructs the updated record, and obtains its new tag from the device. It rechecks the partition table and header before writing, then flushes the write and reads it back. The tool writes a complete 4 KiB logical sector even though the bootloader only consumes the smaller header. This works on nano 5G hardware.

Once the private record and modified font are installed, they remain in NAND across restarts. emCORE and the host computer are needed for the installation workflow, not for each subsequent boot.

A bootloader in less than 28 KB

Reaching the font parser automatically solved persistence. The next constraint was fitting something useful inside the font. I wanted it to load Rockbox from storage, so the payload needed a NAND driver, a flash translation layer, a filesystem reader, and enough startup code to hand off reliably.

To fit, I compiled with size and link-time optimizations and had the linker remove unused sections. The Rockbox kernel is stored on the device’s FAT32 partition and can be easily updated.

Taking control from the font parser

Code execution initially arrives in a damaged FreeType call frame. The stack has been corrupted, and Apple’s OS has left interrupts, DMA controllers, timers, caches, and address translation configured for its own use. Jumping straight into a large C program would carry that state into storage initialization.

I split the bootstrap into two images. The first is the 808-byte assembly stub at 0x22050000. Its job is to leave the parser context: mask IRQs and FIQs, switch to a private stack, stop inherited timer activity, quiesce DMA and clock domains, and clean up caches and the MMU before entering the main payload. It replaces the damaged stack and then jumps to the Rockbox kernel loader.

The second image is the main loader at 0x22060000. Its entry code disables the watchdog before starting the NAND scan, installs its own stack, and clears the uninitialized-data area before calling C. The watchdog matters because reconstructing the logical flash mapping can take several seconds; a reset in the middle would stop the boot before it ever found Rockbox.

This separation keeps the most fragile stage small. The assembly stub establishes a controlled execution environment; the main payload can then do the more substantial storage work in freestanding C.

Reading NAND and starting Rockbox

At the hardware level, the NAND driver uses FMSS, a programmable microcontroller, to communicate with the NAND chips. lemonjesus’s earlier work on the S5L8702 sequencer, published as S5L8702-FMISS-Tools, documents its instruction set and provides tools for inspecting and building bytecode. That research is important prior work for understanding this part of the storage hardware; my work here uses the sequencer to read NAND as part of the nano 5G boot path.

The loader first checks that the microsecond timer used for driver timeouts is running. It then initializes the read-only NAND and FTL stack, mounts the FAT filesystem, and opens /.rockbox/rockbox.ipod. The core sequence follows the Rockbox bootloader’s own file-loading path:

The file loader checks the Rockbox model identifier and checksum, then leaves the executable image at 0x08000000. The final handoff keeps interrupts masked, cleans and invalidates caches, drains pending writes, and branches to that address. Rockbox’s startup code takes over from there. If storage, mounting, or image loading fails, the payload shows the failing stage on the LCD and stops.

Result and limits

On my nano 5G, the result is a cold, battery-powered boot straight into Rockbox, with no USB connection and no disk-mode button sequence. The PRVD partition setting skips rsrc validation and, when combined with the star exploit, enables untethered boot straight into Rockbox. The main constraint is that the font payload is limited to 27,874 bytes. Installation and restoration procedures, along with the reverse-engineering notes and build details, are in the nano5g_bootstub and nano5g_emCORE repositories below.

I have confirmed that the private-data partition works the same way on the nano 7G, which suggests the method will likely work on the 6G too. I plan to get the nano 4G and 5G Rockbox ports into good shape before applying this method to the 6G and 7G.
