Claude needs a telescope

Many moons ago (2023) otel-desktop-viewer had a fairly predictable audience: humans writing and debugging code by hand. As we started handing more of that work to agents, an interface designed for the human visual cortex became a bit awkward. What good is a trace viewer to an agent?

Turns out, they need feedback just as much as humans do, if not more! Without that feedback loop an agent is flying blind. Stopgaps like redirecting stdout to a file for your agent to read or grep work okay, but don’t play well with traces and metrics.

Ideally, you (or rather, your agent) should be able to correlate all three to understand what your application is doing. That makes the difference between your agent burning tokens on printf lines around a network call and jumping straight to the exact error already captured by OpenTelemetry instrumentation.

An agent could try using otel-desktop-viewer through the browser UI, but that’s a slow, expensive way to ask for telemetry. Since otel-desktop-viewer already stores your traces, logs and metrics in an embedded DuckDB database, it made sense to extend the CLI with new commands that agents can use to get at the data directly. Humans get a nice UI, and agents get delicious delicious text.

You don’t even strictly need to know how it works. Just ask your agent to use otel-desktop-viewer and it’ll figure it out:

Use otel-desktop-viewer to find out why checkout is slow and failing in west. Keep it brief.

$ otel-desktop-viewer query Show query
otel-desktop-viewer query "
select
  variant_extract(resource.attributes, 'cloud.region')
    ::varchar as region,
  variant_extract(resource.attributes, 'service.version')
    ::varchar as version,
  count(*) as requests,
  count(*) filter (where status_code = 2) as errors,
  min((end_time - start_time) / 1e6) as min_ms,
  max((end_time - start_time) / 1e6) as max_ms
from spans
where service_name = 'api-gateway'
  and name = 'POST /api/v2/orders'
  and start_time between
    epoch_ns('$OTEL_VIEWER_START'::timestamptz)
    and epoch_ns('$OTEL_VIEWER_END'::timestamptz)
group by 1, 2
order by 1, 2" --endpoint "$OTEL_VIEWER_ENDPOINT" 2>/dev/null

Let’s look at the new commands, how I made the instructions easy for agents to find, and some fun evals to make sure all this actually works well in real tasks!

I wanted investigations to be incremental, so the agent can choose which records deserve a closer look before spending tokens on the details.

A lot of tools dump JSON to the agent. Depending on the shape of your data, that can be a wildly inefficient use of tokens. That’s why otel-desktop-viewer gives your agent a compact table by default. That keeps the token count down for the agent, but is also very human-readable if you ever need to follow along.

TracesTable tokensJSON tokensToken difference
5457618161 fewer (26.1%)
108511,239388 fewer (31.3%)

JSON is sometimes better for an agent if it can pipe the output to other shell commands to pick out precisely the data it needs. If your agent only needs the IDs of traces with errors, it can use --json and filter the results with jq. Out of 20 traces, that leaves four IDs for a whopping 80 tokens.

SQL

Cool, but what if your agent only needs the error type from that stripe/create-charge span?

First it needs to know where to look. The query command accepts read-only SQL, so the agent can use SHOW TABLES to find the spans table and DESCRIBE spans to find the attributes column. Then it can ask for that one field without pulling the whole-ass span into context. 🎉

From there, it can ask DuckDB a broader question: how many stripe/create-charge calls failed in each region?

Compare regions

How many stripe/create-charge calls failed in each region?

otel-desktop-viewer query "
select
  resource.attributes['cloud.region']::varchar as region,
  count(*) as calls,
  count(*) filter (where status_code = 2) as failed
from spans
where name = 'stripe/create-charge'
group by region
order by region"
Raw output
region  calls  failed
------  -----  ------
east    16     0
west    14     2

Two of 14 calls failed in west; none of the 16 in east failed. DuckDB counts the spans and sends back one row per region.

Discoverability

Your agent needs to be able to find the user manual whether it’s installing the viewer for the first time or using one that’s already running. So how do we get the right guidance in front of it, whichever workflow it chooses?

By planting the instructions in all the places where agents are likely to trip over them:

  1. Repository README

    The repository’s README includes installation instructions and a For agents section, so an agent can read the guide before it even installs the viewer or a skill.

  2. CLI help

    The CLI’s --help lists skills first; that command prints the investigation instructions. This makes the guide available from the executable itself, without a separate skill installation.

  3. Viewer homepage

    The homepage links to /llms.txt, which serves the same guide that otel-desktop-viewer skills prints. Both match the version of the viewer you’re running.

  4. Installed skill

    The installable skill makes the instructions available in the agent’s own skill library. Its description helps the agent recognise relevant tasks and load the guide before contacting the viewer.

Evals

“Under the most rigorously controlled conditions of pressure, temperature, volume, humidity, and other variables, the organism will do as it damn well pleases.”

— Harvard Law of Animal Behaviour

So how do we know if we got it right? Can I count on my agent to get the right answer consistently? And how do smaller models hold up? That’s what evals are for.

For this post, I gave 11 models the same shop telemetry and five simple tasks, with three attempts at each. GPT-6.1 Sol graded the answers in fresh conversations without seeing which model wrote them. We can also trace the agent’s path and ingest that into otel-desktop-viewer to see what they’ve done! It’s all deliciously circular.

Short of some light misconfiguration on my part (sorry! 🇨🇦), everyone did really well. The three Flash models even passed 41 of their 45 attempts!

And then there’s Haiku. The little dude means well. It just gets really confused. I asked Haiku the same checkout question three times. Here’s how each attempt went:

  1. Listed ./bin, guessed some HTTP routes, then handed an http:// URL to the file reader.
  2. Grepped the otel-desktop-viewer executable for /api/ instead of running it. Found 30 matches and pulled the string it needed (/openrpc.json) out of the binary, which is certainly one way to do it…
  3. Finally ran --help, opened the guide, and got it right: 4 of 32 customers.

These weird runs give me good information, too. When I checked the tool calls, I could see that Haiku had the right URL, even if it took the scenic route to get there. After all that, my test harness rejected its GET because it used the short-form -m instead of --max-time for the same timeout. That’s fixed now.

Another example: Luna 6 is the reason we have /llms.txt. It kept going straight to the HTTP endpoint and guessing API routes, so I put the instructions in its way.
