Independent .NET for WebAssembly and WASI.

NetWasm is an independent compiler, CoreLib, runtime and SDK that compiles C# and .NET CIL directly to WebAssembly. It does not carry the desktop CLR, Mono, dotnet.js or application DLLs into production.

C# now beats Rust on Wasm size

NetWasm + precise GC: 47,895 bytes

For the same print-42 workload, NetWasm's result includes the runtime and precise Compact garbage collector. Both artifacts are standalone WASI Preview 2 Components, built the way a developer gets them out of the box: each toolchain's standard library and ordinary build, with no hand-added tools.

10.7% smaller raw. 19.5% smaller with Brotli-11.

Toolchain Raw Wasm Brotli 11 Comparison role
NetWasm, Compact GC 47,895 B 13,660 B WASI P2 Component; precise GC included
Rust 1.95.0, size profile 53,635 B 16,963 B Matched WASI P2 Component reference
Kotlin 2.4.0 wasmWasi 79,293 B 22,655 B P1 context; GC supplied by the host engine
TinyGo 0.39.0 93,043 B 26,931 B P1 context; precise GC configured

Rust is the headline comparison because it uses the same workload and output form. Kotlin/Wasm and TinyGo show the broader footprint landscape, but their targets and runtime boundaries differ. This is a measured workload/profile result, not a language-wide size ranking.

NetWasm's figure is the template application's default Release publish. Rust's adds Cargo's documented size settings (opt-level = "z", LTO, one codegen unit, panic = "abort" and stripped symbols) to an ordinary cargo build. Binaryen's wasm-opt is not a post-processing step here: it is part of NetWasm's compiler pipeline and runs in every ordinary build, with nothing to install or enable. Rust's wasm32-wasip2 output is a component, so applying wasm-opt to it means extracting the core module, optimizing it and re-encoding the component by hand.

Both languages can go lower, but that is a different class of program: Rust with no_std, or C# with a minimal library such as bflat's zero library, each giving up most of the standard library and, for C#, the garbage collector.

Versions, settings, desktop figures and reproduction

Hello World is just the smallest example. NetWasm builds real applications too.

C# 15 · JavaScript modules and Web Workers · static .a interop · WIT/WASI P2 · expression trees · HTTP/JSON/XML/Regex · reflection-free DI · TUnit/VSTest · wasm64 · three allocation strategies

Today NetWasm can:

  • build, run, publish and test projects through the ordinary dotnet CLI;
  • publish C# exports as typed JavaScript modules that run in the page or in a Web Worker;
  • link compatible Wasm .a archives and generate bounded C ABI marshalling;
  • generate C# bindings from WIT and produce standalone WASI P2 Components;
  • construct and inspect expression trees without general runtime reflection;
  • use independently packaged LINQ, HTTP, JSON, XML, Regex, Hashing and dependency-injection libraries;
  • dual-target libraries for netwasm0.1 and desktop .NET.

The profile is deliberately smaller than desktop .NET. It already supports complete applications, portable libraries, test projects and browser modules.

Install .NET SDK 10.0.303 or newer, then run:

dotnet new install NetWasm.Templates
dotnet new netwasm-app -n HelloNetWasm
cd HelloNetWasm
dotnet restore
dotnet run
dotnet publish -c Release -o publish/local

Run the published component with a compatible WASI Preview 2 host, such as Wasmtime:

wasmtime run publish/local/HelloNetWasm.wasm

The published component is self-contained with respect to .NET. A WebAssembly host is still required. Build with .NET; run without .NET.

Projects using C# 15 select the .NET 11 SDK; earlier language versions can stay on .NET 10. The SDK restores its pinned Node, LLD and Binaryen tools through NuGet, so an ordinary app does not require a separate Emscripten, Git or Python installation. See the complete quickstart for host, restore, Windows, browser and dual-targeting details.

Roslyn produces CIL. NetWasm compiles the reachable program directly to Wasm, specializes its generics and links only the runtime support it needs. The linked Wasm component is the program.

  • Closed-world compilation. Unreachable code, imports and runtime features do not enter the artifact.
  • A smaller platform contract. NetWasm supports portable APIs instead of reproducing every desktop runtime assumption.
  • No broad runtime reflection. Runtime type names, dynamic assembly loading and the dynamic keyword are outside the profile.
  • Generated boundaries. JSON, DI, WIT and native interop use known contracts rather than runtime discovery.
  • Optional data and diagnostics. Timezone data, rich stack traces and other deployment data are included only when selected.
  • One collector. Only the chosen allocation strategy is linked.

This is a new .NET platform, not desktop .NET squeezed into a Wasm sandbox. That boundary is what makes native-Wasm-sized C# possible.

How JSON and optional features affect size

Choose your allocation strategy

Compact is the default: a size-first, precise, non-moving mark-and-sweep collector. It traces compiler-published roots and reference layouts without conservative scanning. Its name refers to implementation size, not moving heap compaction.

Strategy Best fit Raw component Brotli 11
Compact (default) Small applications and low-churn UI 47,895 B 13,660 B
NetWasmGC Higher allocation throughput 50,855 B 15,053 B
Bump Bounded, one-shot jobs 43,864 B 11,959 B

Select a strategy in the executable project's .csproj:

<PropertyGroup>
  <NetWasmGarbageCollector>NetWasm</NetWasmGarbageCollector>
</PropertyGroup>

Leaving the property unset selects Compact. Libraries remain collector-neutral; all four backends are packaged for wasm32 and wasm64. See Choosing a garbage collector for the tradeoffs and diagnostics.

Libraries should travel upward

A library written for the smaller NetWasm profile should also be useful on desktop .NET, rather than trapped in a Wasm-only ecosystem.

dotnet new netwasm-lib -n MyLibrary

The template targets netwasm0.1 and net10.0, producing NuGet assets for both platforms. This is explicit multi-targeting, not a promise that arbitrary desktop packages work in reverse.

NetWasm.Libraries provides the ported framework and extensions packages. TUnit-NetWasm provides ordinary dotnet test integration through the generic VSTest bridge.

How does this compare to conventional .NET Wasm?

For an empty-UI Blazor WebAssembly application that prints 42, with AOT, managed trimming, IL stripping, invariant globalization and size-focused native linking enabled:

AOT build Uncompressed Wasm Relative to NetWasm
NetWasm, Compact GC 47,895 B 1×
Blazor WebAssembly, .NET 10 12,276,684 B 256×
Blazor WebAssembly, .NET 11 RC1 15,289,241 B 319×

The Blazor total includes its native runtime and required Webcil assemblies; NetWasm includes its runtime, garbage collector and WASI component. This is a console component versus an empty-UI application, not an equivalent-framework comparison or a claim about every .NET workload.

Exact Blazor versions, settings and reproduction

NetWasm is pre-1.0. Its supported profile is usable today and covered by published qualification, but source, package, target-profile and ABI contracts may change between minor releases.

The normal portable output is a wasm32 WASI Preview 2 Component. Raw wasm32, raw wasm64 and JavaScript-host integration are advanced alternatives; wasm64 Components remain blocked by upstream tooling.

Runtime reflection, dynamic, runtime assembly loading and managed threading are outside the profile. General System.IO.File/Directory/FileStream, raw sockets and subprocess APIs are not yet implemented. Existing NuGet packages work only when their reachable code and API dependencies fit the supported profile.

Supported APIs and limitations · Documentation index

NetWasm 1.0 means a useful, documented and stable smaller platform. It does not mean “desktop .NET, but in Wasm.” The main remaining themes are:

  • broader WASI Preview 2 coverage;
  • globalization modes and optional culture data;
  • expression-tree completion;
  • a faster incremental development loop;
  • a stable netwasm1.0 platform and runtime contract;
  • production diagnostics and broader host qualification.

New in NetWasm 0.10.0: rebuilt garbage collectors. Objects carry no collector header, arrays are single allocations, NetWasmGC allocates by advancing a pointer, and Compact has a new core built for size and memory. Allocation-heavy programs run faster and use far less memory, and applications that ship time zone data start in a fraction of the time. The Boehm collector is removed. Release notes

In progress: broader compatibility with existing .NET Standard 2.1 library binaries and NuGet assets. The target is to consume libraries unchanged when their reachable code fits the NetWasm profile, without carrying unused unsupported paths into the application.

This does not turn NetWasm into desktop .NET. Reachable general runtime reflection, dynamic, runtime assembly loading, managed threading, unsupported host APIs and named-culture globalization remain outside the initial compatibility slice and fail at compile time.
